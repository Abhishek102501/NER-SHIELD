# NER-SHIELD Agent Service

The AI Disaster Response Agent: LLM orchestration, typed tool calling, a controlled
ReAct-style loop, and RAG retrieval over a disaster-management document corpus. A separate
FastAPI process from `ml-service` (the trained rainfall/landslide model service) — LLM/agent
dependencies never entangle with that runtime.

**Architecture**: Frontend → Spring Boot (`POST /api/agent/query`) → this service → LLM +
tools (which call back into Spring Boot's existing REST APIs) + RAG (Postgres). This service
never talks to the database except for the isolated `agent` schema (RAG), never executes SQL
generated by the model, and never writes operational data directly — every read or write
against threats/incidents/risk-zones/alerts/field-reports/response/dispatch goes through the
same public Spring Boot API the frontend uses.

## Hard safety guarantees (structural, not just prompted)

- **No LLM configured → no fabricated answer.** `LLM_PROVIDER=none` (the default) or a
  missing `LLM_API_KEY` makes every `/query` call return `available: false` with an explicit
  `reason` — there is no code path that can synthesize a response in that state (see
  `llm/unavailable_provider.py`).
- **`create_dispatch` never executes automatically.** If the model calls it, the agent loop
  (`agent/loop.py`) intercepts the call before it reaches the tool handler and returns a
  `proposedAction` instead. The handler only ever runs from the explicit
  `confirmedAction` path in `main.py`'s `/query` endpoint — a second, separate request the
  caller sends only after a human confirms.
- **No arbitrary code/SQL execution.** Tools are a fixed, typed list (`tools/registry.py`).
  There is no "run this Python/SQL" tool.
- **Tool outputs and retrieved documents are data, not instructions** (prompt-injection
  defense) — enforced via the system prompt in `agent/loop.py`, not just a convention.
- **No fabricated embeddings/documents.** If no embedding provider or RAG database is
  configured, `search_knowledge_base` returns `available: false`, never an empty-but-silent
  success or an invented document.

## Environment variables

Copy `.env.example` to `.env` (git-ignored) and fill in real values. Never commit secrets.

| Variable | Purpose |
|---|---|
| `BACKEND_BASE_URL` | The Spring Boot backend's base URL (default `http://localhost:8085`) |
| `LLM_PROVIDER` | `anthropic` or `none` (default) |
| `LLM_API_KEY` | Anthropic API key — required if `LLM_PROVIDER=anthropic` |
| `LLM_MODEL` | Default `claude-sonnet-5` |
| `LLM_MAX_TOOL_ITERATIONS` | Bound on the ReAct loop (default 6) |
| `EMBEDDING_PROVIDER` | `voyage` or `none` (default) |
| `EMBEDDING_API_KEY` | Voyage AI API key — required if `EMBEDDING_PROVIDER=voyage` |
| `EMBEDDING_MODEL` | Default `voyage-3` |
| `RAG_DATABASE_URL` | Postgres connection string for the `agent` schema (same instance as the main backend). Leave empty to disable RAG entirely. |

## Running locally

```bash
python -m venv .venv
.venv/Scripts/activate   # or source .venv/bin/activate on Linux/macOS
pip install -e ".[dev]"
cp .env.example .env     # then edit .env
uvicorn agent_service.main:app --host 0.0.0.0 --port 8100
```

Health check: `GET http://localhost:8100/health`.

## Running via Docker

```bash
docker build -t nershield-agent-service .
docker run --rm -p 8100:8100 --env-file .env nershield-agent-service
```

No `docker-compose.yml` existed anywhere in this project before this change — the rest of
NER-SHIELD (backend/frontend/ml-service) runs natively in local development, so this
Dockerfile is provided standalone rather than wired into a compose file that doesn't exist.

## Configuring the LLM

Set `LLM_PROVIDER=anthropic` and `LLM_API_KEY=<your key>`. No other code change is required.
Adding a second provider means writing one new class implementing `llm/base.py`'s
`LLMProvider` and registering it in `llm/factory.py`.

## Configuring embeddings / RAG

1. Set `EMBEDDING_PROVIDER=voyage`, `EMBEDDING_API_KEY=<your key>`.
2. Set `RAG_DATABASE_URL` to the same Postgres instance the Spring Boot backend uses (the
   `agent` schema is created by `backend/src/main/resources/db/migration/V5__agent_rag_schema.sql`
   — run the backend once, or `mvn -o flyway:migrate`, so that schema exists first).
3. Ingest a real document:

```bash
python -m agent_service.rag.ingest \
    --title "NDMA Guidelines on Landslide Management" \
    --organization "National Disaster Management Authority" \
    --source-url "https://ndma.gov.in/..." \
    --document-type "guideline" \
    --document-date 2024-01-01 \
    --file path/to/extracted-text.txt
```

**The knowledge base ships empty.** No document content is included in this change — see
"Corpus status" below. Never invent document text and pass it through the ingester as if it
were a real source.

### pgvector note

This project's PostgreSQL 16 instance does not have the pgvector extension installed
(confirmed: no `vector.control`/`vector.dll` under the install tree, and
`pg_available_extensions` lists no `vector` row — unlike PostGIS, which was present but
merely not enabled). The RAG store (`rag/store.py`) therefore stores embeddings as plain
`double precision[]` columns and computes cosine similarity in Python at query time — real,
unfabricated similarity search, just without an ANN index. See that file's module docstring
for the exact migration path once pgvector is installed.

## Corpus status

**Not populated.** This change adds the ingestion mechanism (`rag/ingest.py`), the isolated
schema (`agent.documents`, `agent.document_chunks`), and the retrieval/tool wiring — but no
actual NDMA/NDRF/IMD or other document content ships with it. Populating the corpus requires
someone to obtain real, attributable official documents and run the ingester against them.
Until then, `search_knowledge_base` will report zero matches (the store is genuinely empty,
which is different from — and more honest than — `available: false`, which means no
embedding/database configuration exists at all).
